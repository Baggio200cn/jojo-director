01导学：什么是 AGENTS.md？

当学生（或您自己）让 AI 帮忙写代码时，AI 每次打开项目都像一个"第一天报到的实习生"：没有记忆、不了解规矩、不知道哪些东西不能碰。AGENTS.md 就是贴在车间门口的《岗位操作规程》——AI 代理每次开工前必读。

教学类比：实训车间里，新来的学生第一天会拿到《实训指导书》和《安全操作规程》：先学什么、用什么工具、哪些设备绝对不能动。AGENTS.md 之于 AI 编程代理，正如实训指导书之于实训学生——它管的不是"会不会做"，而是"按谁的规矩做"。

为什么老师需要懂它？

① 学生已经在用
学生用 Cursor、Claude Code、Codex 等 AI 工具写课程设计、毕业设计代码已是常态。不懂规则，就无法评价"AI 写的代码为什么是这个样子"。
② 它是新的教学抓手
AGENTS.md 把"工程规范"从口头要求变成 AI 可执行的书面约束——这本身就是一堂生动的"工程伦理与规范"课。
③ 规则需要人把关
本报告会展示：这些规则写得越"硬"，在生产环境越危险。谁来踩刹车？——懂业务、懂教学场景的人。

本报告分析的规则原文

以下 7 条规则摘自一份真实的 AGENTS.md 项目守则（原文为英文，本报告逐条翻译、解读并用真实项目验证）：

# AGENTS.md
1. Do not preserve backward compatibility. （不保留向后兼容）
2. Choose the simplest implementation... （最简实现，拒绝投机性抽象）
3. Grow the system in layers. （分层演进，先闭环再加厚）
4. Keep components modular... （模块化，关注点分离）
5. Prefer established, well-maintained libraries... （优先成熟库）
6. Lean on the dependencies already in the project... （先榨干已有依赖）
7. Make architectural decisions for the long term. （架构面向长期）
阅读提示：这 7 条规则的隐含假设是——绿地项目、单一团队、快速迭代、变更成本低。它是一份优秀的"防屎山"军规，但绝不是生产环境的免死金牌。第 ③、⑤ 节会展开论证。

02案例项目解剖：JOJO Director 是什么？

本报告全部案例取自 JOJO Director——一个真实部署、真实收费的职业教育微课 AI 创作画布（当前正运行在 https://115.190.155.2）。它不是教学玩具，而是一条"教学准确性优先"的微课生产产线。

项目一句话：从一段文字脚本开始，自动完成 脚本 → 分镜 → 首/尾帧 → 视频 → AI 质检 → 拼接成片 的全流程，产出带字幕字卡的教学微课视频。

与通用 AI 视频工具的区别：通用工具判断"这张图美不美"，JOJO Director 判断"这张图对不对"——因为一部画面华丽但把占空比讲错的微课，比没有微课更糟糕。

代表作：《LED 驱动器与智慧照明控制》微课，12 个镜头 / 2 分 08 秒 / 全程无人工剪辑。

03七条军规逐条精讲

点击每条规则展开。每条规则四个视角：规则解读（它到底在管什么）→ JOJO 真实案例（该项目里的真凭实据，含文件路径与代码）→ 生产环境红线（为什么不能照抄）→ 课堂讨论（可直接用于教学的提问）。

1

不保留向后兼容生产风险：高

"Do not preserve backward compatibility. Remove obsolete paths instead of adding compatibility layers, fallbacks, or migrations."
▶

直译：直接删除过时的代码路径，不要添加兼容层、回退逻辑（fallback）或迁移脚本。

在管什么：防止"兼容层叠兼容层"的死代码堆积。接口变了就删旧的，让代码库永远只有一种实现，AI 代理（和人类新人）不会被"到底该调哪个"搞糊涂。

教学类比：实训设备更新换代后，旧机床的操作规程必须从指导书上撕掉，而不是"新规程第 5 章 + 旧规程附录 B 混合使用"——学生一定会拿错。
违规现场 A：双胞胎入口

仓库里同时存在 backend/main.py（1006 行）和 backend/app/main.py（1026 行）。根目录那份是早期版本残留，它甚至用了相对导入（from . import auth），作为顶层脚本根本无法运行——一条纯粹的"死路径"。按规则 1，它应立即删除。

违规现场 B：legacy 提示词墓地

backend/prompts/legacy/ 里保留着 6 份旧系统提示词（agent_system.md、storyboard_system.md、qc_judge_system.md 等），现役代码已不再引用它们。

值得深思的反例：救命用的 fallback

但现役代码里仍有一段"规则 1 明令禁止"的兼容逻辑（app/main.py 第 538–575 行）：

legacy_last = (shot.get("last_frame_prompt") or "").strip()
# ……新字段 last_delta 优先，旧字段 last_frame_prompt 兜底：
elif last_delta or (legacy_last and legacy_last != first_p):
    delta = last_delta or (f"apply the end-state change described here: {legacy_last}")

为什么留着？因为数据库里已存量的分镜数据用的还是旧字段，删掉兜底逻辑，老项目就打不开了。这正是"代码洁癖"撞上"真实数据"的瞬间——也是本报告反复强调的：规则 1 的前提是你掌控全部数据。

为什么这是生产上最危险的一条：

① 有真实用户和数据——JOJO 的 jojo.db 里躺着真实用户项目，删除旧字段解析 = 老项目当场损坏；
② 无法原子切换——服务滚动发布时新旧版本共存，没有兼容层必然报错；
③ 回滚依赖兼容——新版写入新格式数据后，回滚到旧代码反而读不懂自己的数据。

生产版改写："可以删，但要按流程删"——标记 deprecated → 监控调用量 → 灰度迁移存量数据 → 确认零调用后删除。

课堂讨论题：
  • 如果你带的学生在做课程设计，"删掉旧代码"和"保留旧代码"各自的风险是什么？
  • JOJO 把旧提示词留在 legacy/ 文件夹，算"兼容层"吗？它和代码里的 fallback 分支有什么本质区别？（提示：一个占磁盘，一个占逻辑）
  • AI 代理被命令"不要兼容"，它会不会把数据库里还在用的旧字段解析也一起删掉？谁来踩刹车？

    最简实现，拒绝投机性抽象生产风险：中

    "Choose the simplest implementation that fully meets the current requirements. Avoid speculative abstractions, configuration, and indirection."
    ▶

    直译：选择能完整满足当前需求的最简实现；避免投机性的抽象、配置项和间接层。

    在管什么：即 YAGNI 原则（You Aren't Gonna Need It）。AI 代理特别爱"秀肌肉"——让一个函数支持 8 种未来场景、提前设计插件机制。这条规则摁住它：只解决今天的问题。

    教学类比：学生做课程设计时，要求"设备能完成本次加工任务"即可，而不是先画一张"未来五年柔性产线"的蓝图却连一个零件都车不出来。
    正面样本 A：91 行的数据库层

    backend/app/db.py 全文 91 行，手写 sqlite3，没有引入任何 ORM 框架。但它的 docstring 写着一句深思熟虑的话：

    """第一阶段用 SQLite，字段与 PostgreSQL 兼容，后续可无痛迁移。"""

    注意：它没有为迁移写任何抽象层（那违反规则 2），只是在字段命名上留了余地——这是"最简实现"与"面向长期"（规则 7）握手的教科书姿势。

    正面样本 B：确定性路由，而非智能体框架

    MAAO 路由引擎本可以做成一个"会思考的规划 Agent"，实际是 capability_map.yaml 里一组按序执行的确定性规则（_route_shots）。能力档位纪律也极简：证据不足 3 次一律 UNKNOWN——用一条纪律替代一套统计模型。

    红线："当前需求"的边界本身就是架构判断。多租户、审计日志、权限、限流不是"投机"，而是商用产品的必然项——JOJO 后来补"双通道登录+限额+全站熔断"（commit 804867d）正是路线图上的必然需求。如果最初的数据模型把用户体系定死，补这些能力就是重写。

    生产版改写：实现层面从简，但核心数据模型要开过"需求边界评审"再定稿。

    课堂讨论题：
  • "为将来预留"和"投机性抽象"的分界线在哪里？JOJO 的 SQLite 方案属于哪一边？
  • 如果让 AI 代理"自由发挥"设计微课项目的数据表，它大概率会加哪些用不上的字段？

    分层演进：先有能跑的闭环，再逐层加厚生产风险：低

    "Grow the system in layers... Never trade a working product for unfinished complexity."
    ▶

    直译：从端到端能跑通的最小版本开始，每个新能力都叠加在"已经可用的产品"之上；永远别拿能工作的产品去换未完成的复杂架构。

    在管什么：防"憋大招式重构"。AI 代理很容易答应"我给您重写成微服务架构"，然后留下一个两周都跑不起来的半成品。

    教学类比：实训教学先让学生用普通车床完整车出一个合格零件（闭环），再学数控、再学产线——而不是第一节课就拆一台加工中心。
    完美执行：git 历史就是证据

    JOJO 的第一个提交（0b95c05）就是端到端可用的完整产品——首页输入"今天要做点什么微课？"，走完 脚本→分镜→帧→质检→视频→拼接 全链成片。此后 5 个提交全部是叠加在可用产品上的增量：

    提交性质叠加了什么
    c3396e8修复字幕字体跨平台（Windows msyh / Linux Noto CJK）——上 Linux 服务器才发现的问题
    c168dbd修复补 python-multipart 依赖
    804867d新能力双通道登录 + 邀请码限额 + 全站熔断（商用化）
    e7f2e84/b1af190打磨Agent 建节点自动生成内容 / 导航按钮细节

    没有一个提交让产品处于"跑不起来"的状态——这正是规则 3 的理想形态。

    红线："能跑（works）"在生产环境的定义包含非功能需求：监控、告警、日志、备份。一个"能生成视频但毫无可观测性"的版本，在教学演示里算 works，在收费商用里不算。

    生产版改写：最小闭环里必须包含最小可观测性（至少：错误日志 + 任务台账，JOJO 用 model_tasks 表记录了每次模型调用的 token 与费用，可作正面参照）。

  • JOJO 把"字幕字体跨平台"留到上线后才修——这违反规则 3 吗？（提示：闭环的"环"是指什么）

    模块化，关注点清晰分离生产风险：低

    "Keep components modular and concerns clearly separated."
    ▶

    直译：保持组件模块化，关注点清晰分离。

    在管什么：经典分层原则：UI、业务逻辑、数据访问各自独立、接口明确，便于测试、替换和多人协作。

    教学类比：产线的工序分工——下料、加工、质检、包装各工位职责清晰，换任何一个工位的设备都不影响其他工位。
    正面样本 A：目录级模块化做得相当好

    gateway/（ark、bjmoma 双模型网关）、render/（9 个代码渲染模块）、db.py、auth.py、config.py 各司其职；质检规则按学科外置成 YAML（machine_vision.yaml、kinematics.yaml、optics.yaml……），提示词也整体外置到 prompts/——换学科、换模型、换提示词都不必改代码。

    正面样本 B：AI 系统设计里的关注点分离

    JOJO 的质检体系刻意"判官与教练分离"——给改进建议的 Agent 和打分的 Agent 是两个独立角色，防止"自己改的作业自己打分"的亲缘偏差。这是关注点分离思想在 Agent 编排层面的延伸，值得在课堂上重点讲。

    诚实记录：两个"上帝文件"

    backend/app/executors.py 1915 行、frontend/src/App.tsx 1751 行。目录级模块化做到了，文件级仍然巨型——所有任务类型的执行逻辑挤在一个文件里。真实项目很少是规则的满分答卷，这正是拿真实仓库上课的价值：学生能看到"做对了一半"长什么样。

    红线：本条几乎无争议，唯一的生产提醒是：模块化边界一旦暴露为网络接口（微服务化），"清晰分离"就附带了运维成本——别为了模块化而分布式。
    课堂讨论题：
  • 打开 executors.py 的目录索引，让学生尝试为它设计一个拆分方案：按什么维度拆？（任务类型？模型厂商？同步/异步？）
  • "判官与教练分离"对应传统软件工程里的什么实践？（提示：测试与开发分离 / 审计与执行分离）
    • 5

    优先成熟库，不重复造轮子生产风险：低

    "Prefer established, well-maintained libraries when they reduce overall complexity or improve reliability."
    ▶

    直译：当成熟、维护良好的库能降低整体复杂度或提升可靠性时，优先使用；没有明确理由不要重新实现常见功能。

    在管什么：AI 代理有"即兴手搓"倾向——它写一个日期解析函数只要 5 秒，但那 5 秒的产物没有时区处理、没有边界测试。成熟库背后是成千上万用户踩过的坑。

    教学类比：加工标准件（轴承、螺栓）直接采购国标件，只有自己产线特有的非标件才开模定制。
    关键决策：画布不自研

    JOJO 的核心交互是节点式画布。自研一套可拖拽、可缩放、带连线的画布引擎是数月级工作量，项目直接采用成熟库 @xyflow/react（React Flow 的官方继任者），把全部精力投入真正差异化的部分：质检断言、路由引擎、代码渲染。

    成熟库变成产品竞争力

    后端 8 个依赖各司其职：fastapi 提供 API 与交互式文档，faster-whisper 本地语音转写字幕（模型 faster-whisper-small 就放在仓库 models/ 里），matplotlib 撑起整个代码渲染通道，视频合成调用系统级 ffmpeg。没有一项核心功能依赖自研基础设施。

    红线："成熟"≠"安全"。生产引入第三方库必须过供应链审查：许可证是否兼容商用、有无未修复的 CVE 漏洞、维护是否活跃（JOJO 选用的 oxlint、xyflow 均为活跃项目）。教学场景还涉及一个问题：某些库的学习版许可证能否用于学校商用项目，需要核实。
    课堂讨论题：
  • 什么情况下"自研"反而是对的？（提示：JOJO 的质检断言引擎是自研的——为什么这个轮子值得自己造？）
  • 让学生查一个常用库的 GitHub：最近提交时间、issue 响应速度、Star 数——写一份 3 句话的"能否采用"结论。

    先榨干已有依赖，再谈新增生产风险：低

    "Lean on the dependencies already in the project... Do not assume a library lacks a capability without checking its documentation and types."
    ▶

    直译：先充分利用项目里已经安装的依赖，再考虑自己实现或添加新包；不要在没有查过文档和类型定义的情况下，假设某个库没有某功能。

    在管什么：这是专门针对 AI 代理"知识截止日期"毛病的规则——模型训练数据里某库还是旧版本，它就以为某功能不存在，于是手搓一份或再装一个新包，导致依赖膨胀、实现分裂。

    教学类比：实训前先盘点工具柜里已有的工装夹具，而不是缺什么就先填采购单。
    正面样本：一个 matplotlib 长出整条产线

    项目要画"必须严谨"的教学图——PWM 波形、迈克尔逊干涉光路、设备框图、透镜聚焦。这些图没有引入任何新库（没用 manim、没装图形引擎），全部基于已有的 matplotlib 写成 app/render/ 下 9 个模块：pwm_waveform.py、michelson_lightpath.py、block_diagram.py、lens_focus.py、spectrum_recipe.py……零幻觉、零 API 费，还顺带解决了"AI 画图把占空比画错"的教学事故风险。

    反面教材：一次真实的"没查文档"事故

    git 提交 c168dbd 的原文："fix: requirements 补 python-multipart（上传接口依赖）"。FastAPI 的文件上传依赖 python-multipart，文档里写得清清楚楚，但开发时没查，直到上传接口在生产报错才补上。这条 commit 就是规则 6 的活教材：库的能力边界，以文档为准，不以记忆为准。

    红线：本条本身安全，真正的生产价值在于防依赖膨胀：AI 代理每写一个功能就 npm install 一个新包，半年后 node_modules 变成无法审计的噩梦。生产上应配套"新增依赖需人工审批"的 CI 门禁。
    课堂讨论题：
  • 让学生打开自己项目的 package.json/requirements.txt，逐个回答："这个包提供的功能，我用的那个包真的做不到吗？"
  • python-multipart 这类事故，用什么样的 AGENTS.md 条款可以预防？

    架构面向长期，拒绝权宜之计生产风险：中

    "Make architectural decisions for the long term. Do not accept a stopgap that only works for now and is meant to be replaced later."
    ▶

    直译：架构决策要面向长期；不要接受"暂时能用、打算以后再换"的权宜之计。

    在管什么：与规则 2 形成刻意的设计张力——实现层面要最简（规则 2），但模块边界、数据流向、核心抽象不许欠技术债（规则 7）。简的是代码量，不是思考量。

    教学类比：车间可以只买一台机床（最简），但供电、气路、地基必须按整个车间的规划施工（长期）——设备能加，地基不能重打。
    样板工程：为"模型一定会换代"而设计的架构

    AI 项目最确定的长期事实是：模型一定会更新换代。JOJO 的应对不是"到时候再说"，而是一套制度化的架构（capability_map.yaml）：

    机制真实内容
    能力四档HIGH / MEDIUM / LOW / UNKNOWN，证据 < 3 次一律 UNKNOWN
    证据台账质检判决自动回写 model_tasks 表，能力档位由证据驱动而非拍脑袋
    热加载能力地图改档无需重启服务
    更新纪律文件头明文规定："换模型（ark-model-watch 提醒）必须重测后再改档"
    损失度量Route Regret 报表——LED 微课 ¥59 成本中 47%（¥27.7）是"明知模型不行还往上撞"的浪费，路由引擎的目标就是把它归零
    被拒绝的权宜之计

    面对"AI 画图把电路拓扑画错"，权宜之计是"提示词里多求求模型别画错"；JOJO 选择的长期解是代码渲染通道——严谨图一律程序生成。权宜之计能撑过一次演示，撑不过一百个知识点。

    红线：这是七条里最"理想主义"的一条。生产现实中，有时权宜之计就是正确决策——大促前三天、线上事故止血、合规 deadline 面前，"先扛住、后重构"可能是唯一选项。关键不是拒绝 stopgap，而是每个 stopgap 必须有偿还计划（工单、负责人、截止日期），否则它会悄悄变成永久架构。

    元层面风险（给 AI 立规时尤其注意）：规则 1 + 规则 7 组合起来，等于授权 AI 代理"激进删代码、拒绝渐进过渡"。人类工程师会自己掂量上下文，AI 倾向字面执行——它不知道哪个"过时路径"还被某个低频但关键的批处理任务依赖着。生产仓库的 AGENTS.md 必须加护栏条款（见第 ⑤ 节）。

    课堂讨论题：
  • JOJO 的 db.py 只有 91 行（规则 2 的胜利），却声明"字段与 PostgreSQL 兼容"（规则 7 的伏笔）。为什么这不矛盾？
  • 请学生从自己的项目里找出一个"权宜之计"，并评估：它有偿还计划吗？
  • 如果学校要把 JOJO 部署给全专业 300 名学生用，capability_map 的哪条纪律最需要保留？

    • 04规则之间的张力：军规也会"打架"

    七条规则不是七条孤立的禁令，它们之间存在精心设计的张力。点击下面天平的任意一侧，看看冲突时如何取舍。

    张力一：规则 2（最简实现）⚖ 规则 7（面向长期）

    站规则 2 的观点

    "数据库层就应该 91 行手写 SQLite。任何为迁移预留的抽象层——接口隔离、仓储模式——都是投机，今天用不上就是浪费。"

    👉 点击看裁决

    ⚖️
    站规则 7 的观点

    "项目注定商用、数据注定增长，第一阶段就该上 PostgreSQL + ORM，否则迁移那天就是事故那天。"

    👉 点击看裁决

    ⚖ 裁决：部分成立。JOJO 确实这么做了，而且成功了——但它留了一个关键伏笔：docstring 明文声明"字段与 PostgreSQL 兼容"。最简的是实现，不是设计。这个伏笔不花一行代码，却把未来的迁移成本从"重写"降到"搬运"。
    ⚖ 裁决：过度了。第一阶段上 PG + ORM 会直接拖慢"5 分钟跑通"的快速上手目标（见 README 快速上手节）。但警惕一种伪装：把"我懒得想"包装成"我遵循 YAGNI"。规则 2 减免的是代码量，不是思考量——JOJO 为 SQLite 方案写下迁移注释，正说明它认真想过长期。

    张力二：规则 1（删无赦）⚖ 生产数据（删不得）

    JOJO 仓库里同时存在规则的两种命运：该删没删的（根目录 main.py 死路径、prompts/legacy/ 旧提示词、dist_old/ 旧构建、jojo.db.smoke.bak 备份）与 想删不能删的（last_frame_prompt 旧字段的兜底解析——数据库里还有存量数据）。

    这给课堂一个极真实的结论：规则管得住代码，管不住数据。代码里的过时路径可以"删无赦"，数据里的历史格式必须"按流程退役"。一个人工智能项目真正的资产往往不是代码，而是积累的数据与证据台账——JOJO 的能力地图证据计数就是例证。

    05生产环境红线：从"绝对禁令"到"默认倾向 + 例外流程"

    这份 AGENTS.md 的隐含假设是：绿地项目、单一团队、快速迭代、变更成本低。进入生产环境（真实用户、真实数据、真实收费）后，必须按下表降级使用：

    规则生产风险生产版改写
    1. 不保留兼容高"可以删，但要按流程删"：deprecated 标记 → 调用量监控 → 存量数据灰度迁移 → 零调用后删除。涉及数据库 schema、API 契约、消息格式的变更豁免此条。
    2. 最简实现中区分"投机"与"路线图上的必然"（多租户、审计、限流）。核心数据模型定稿前过需求边界评审。
    3. 分层演进低基本安全。注意"能跑"必须包含最小可观测性：日志、告警、台账、备份。
    4. 模块化低无争议。提醒：别为模块化而分布式。
    5. 成熟库低加一道供应链审查：许可证、CVE、维护活跃度。
    6. 榨干依赖低配套 CI 门禁：新增依赖需人工审批，防 AI 代理装包成瘾。
    7. 拒绝权宜之计中允许 stopgap，但必须带偿还计划（工单 + 负责人 + 截止日期）。

    给 AI 代理立规时的三条护栏条款（可直接抄进 AGENTS.md）

    🛑 删除前确认
    删除任何对外接口、数据格式、文件路径前，必须列出受影响面并等待人工确认。AI 不知道哪个"过时路径"还连着低频但关键的批处理。
    🛡 契约豁免
    数据库 schema、API 契约、消息队列格式的变更不适用"删无赦"，必须附带迁移方案与灰度计划。
    ↩ 回滚方案
    任何破坏性变更必须写明回滚步骤——新版写入的数据，旧版代码必须还能读。
    一句话总结本节：规则的内核（反过度设计、渐进演进、复用优先）是健康的工程文化；缺了灰度、观测、回滚、下线流程这些生产级机制，"保持代码库干净"的代价就是线上事故。

    08总结：把规矩写在纸上，把刹车握在手里

    三条核心结论

    ① AGENTS.md 是"给 AI 的实训指导书"——它把工程规范从口头要求变成 AI 可执行的书面约束，这本身就是一种可教学、可考核的职业素养。

    ② 七条军规的内核（反过度设计、渐进演进、复用优先）在任何项目里都成立；JOJO Director 的真实仓库证明：照着做的项目确实保持了 8 个依赖、清晰的目录与连贯的演进史。

    ③ 但规则 1（删无赦）、规则 2（需求边界）、规则 7（拒绝权宜）在生产环境必须降级为"默认倾向 + 例外流程"，并配上灰度、观测、回滚机制——JOJO 代码里保留的 legacy_last 兜底逻辑，就是"真实数据战胜代码洁癖"的活证据。
