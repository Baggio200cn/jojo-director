# LOOP 执行循环律

> **一切超过 60 秒的工作必须后台化，一切跨网调用必须假设会断，一切循环必须能从断点续起。**

白话：AI 产线里最贵的不是算错，是**等丢了**——任务明明在跑，调用方却因为超时、
断网、进程重启而失去了它的下落。LOOP 律管的就是"发起一件慢工作之后，
怎么可靠地等到它的结果"。

## 条款

**L1 后台化红线（60 秒规则）**
凡是可能超过 60 秒的执行（视频生成、参考视频切分、素材增强、拼接合成、语音合成），
HTTP 接口只负责"受理"，立即返回 `{status: running}`；真正的工作进后台任务，
结果写库。任何依赖"HTTP 连接一直开着等结果"的设计都是定时炸弹——
网关、浏览器、家宽 NAT 都会在你不知道的时刻掐掉它。

**L2 轮询是唯一可信的等待方式**
调用方拿到 running 后靠轮询节点状态取结果。推送/长连接可以做加速优化，
但正确性必须建立在轮询之上：断了连，重新问一遍就是。

**L3 断连转轮询，重试有上限**
跨网调用（家宽→云端、云端→模型厂商）失败时：先重试（固定次数+间隔），
重试期间若发现任务其实已受理，转入轮询而不是重复提交。
禁止无限重试，禁止把"连接断了"当成"任务失败了"。

**L4 断点自愈**
进程可能在任何时刻死掉。重启时必须处理遗留状态：卡在 running 的节点
复位为 failed（附"因服务重启中断"说明），让用户能一键重跑，
而不是永远转圈。

**L5 循环按图走，不按记忆走**
批量驱动（逐镜产线、链式执行）每一轮都从数据库重新读图、找下一个该跑的节点，
而不是在内存里存一份计划清单。计划会过期，图不会。

## 实证案例（迈克尔逊验收九缺陷中的 4 个）

| 缺陷 | 现象 | 修法（条款） |
|------|------|--------------|
| ① 同步长请求被掐 | ref_video 切分跑 3 分钟，网关 60 秒超时掐断，前端报错但后台其实还在跑 | 长任务全部后台化+轮询（L1/L2） |
| ⑨ 家宽长连接不稳 | 本机驱动脚本连云端，跑批中途 ConnectionReset，整批中断 | 驱动器断连重试+转轮询（L3） |
| ④′ 重启后僵尸节点 | 服务重启后节点永远显示 running，用户无法重跑 | 启动自愈：running 复位 failed（L4） |
| ⑦ 按假设名字跑批 | 驱动器硬编码"镜头N首帧"节点名，改名后整批空转 | 每轮从图动态遍历（L5，与 GRAPH G4 共享） |

## 落地检查清单

- [ ] 新增执行器时：预估最坏耗时，>60s 必须进 main.py 的后台任务集合
- [ ] 写驱动/批处理脚本时：外层循环 = 读图→找可跑节点→执行→轮询，无内存计划表
- [ ] 所有 requests 调用：显式 timeout + 重试装饰 + "断连后先查状态再决定重发"
- [ ] 服务启动逻辑里有 running→failed 的自愈复位
- [ ] 验收方法：跑一个长任务，中途 kill 服务/断网，恢复后系统状态可解释、可续跑
